# CRM duplicate protection — Phase 0 audit (2026-10-30)

Read-only audit of `main` at `523764d` before any change. Scope: CRM schema, identity model, normalization, every write
path into contacts/leads, uniqueness, imports, outreach queue, suppression, deployment.

## 1. What existed

| Area | State before this change |
|---|---|
| Tables | `companies`, `contacts` (raw `email` NOCASE, raw `phone`), `leads` (CHECK on `source`, `stage`), `crm_activities`, `organizations` + `memberships` (customers), `users.email` UNIQUE NOCASE |
| Normalized keys | `contacts.email_norm`, `phone_norm`, `name_company_norm` (0044, trigger-maintained, indexed). `phone_norm` = 10 digits with the US `1` dropped: not E.164, ambiguous for non-US numbers |
| Uniqueness on identifiers | **None.** Any number of contacts could hold the same email or phone |
| Duplicate handling | After the fact: `crm-dedupe.ts` groups leads sharing email/phone/name+company, staff merge or dismiss (audited, history kept) |
| Multiple phones/emails per business | Not supported (one `email`, one `phone` column per contact) |
| Verification / provenance of contact values | Not recorded |
| Outbound calling | `voice_outbound_requests`: three consented purposes only (callback, consultation reminder, support follow-up); staff approval, per-purpose consent, `voice_dnc`, calling window, per-number caps; the **request** is claimed atomically, but nothing stopped two **requests for the same number** from both being approved and dialled (only the daily cap limited it) |
| Email suppression | `email_suppressions` (hard bounce, complaint). No unsubscribe table; no marketing automation exists (marketing mail is refused without an unsubscribe link) |
| Onboarding | `onboarding_responses` is one row per project (`ON CONFLICT(project_id)`): already duplicate-safe |
| Research / CRM import API | Did not exist |

## 2. Write paths into contacts and leads (all bypassed identity checks)

| # | Path | Behaviour before |
|---|---|---|
| 1 | `leads.ts captureLead` — `/contact`, `/quote`, `POST /api/leads` | Always a new company + contact + lead |
| 2 | `voice.ts createCallLead` — 5 receptionist functions | Always a new contact + lead (one per call) |
| 3 | `crm.ts createManualLead` — `/staff/crm/new` | Always new |
| 4 | `crm.ts updateContact` — lead page edit | Could set an email/phone used by another record silently |
| 5 | `billing.ts ensureCheckoutLead` | Linked an open lead by exact email, else new contact |
| 6 | `crm-dedupe.ts mergeLeads` | Fills blank contact fields on the survivor |
| 7 | `auth.ts`, `quotes.ts` | Link `contacts.user_id` by email |
| 8 | `privacy.ts`, `voice-ops.ts` | Erasure blanks name/email/phone |
| 9 | `scripts/seed-staging.ts` | Row dump replayed with `INSERT OR IGNORE` |
| 10 | `voice-outbound.ts requestOutbound` | New request per call, even for a number already queued |

## 3. How each path is covered now

- **All contacts writes (1–9 and any future path):** SQLite triggers on `contacts` (migration 0047) register canonical
  identities and links on every insert/update and scrub them on erasure. Nothing can write a contact without its
  identifiers being registered.
- **Decisions (1, 2, 3, research/CRM API):** go through `contact-identity.ts intake()` — create / link / update / merge /
  hold / suppress / reject, atomic per decision, race-guarded, idempotent, recorded in `crm_intake_decisions`.
- **Edits (4):** allowed (shared lines are real) but recorded field by field and sent to review when they collide.
- **Checkout (5):** unchanged logic (the buyer is a verified account holder); identities registered by the triggers.
- **Outbound (10):** one open request per number (guarded insert) and a number-level lease in `phone_outreach_ledger`.
- **Seed (9):** derived identity tables are excluded from the dump (regenerated by the triggers).

## 4. Read-only duplicate audit

This session has no access to production or staging D1 (no Cloudflare credentials), so the historical audit was not
run against real data. `scripts/crm-duplicate-audit.ts` is the read-only tool for that (RUNBOOK §4). It was run
against a database built from migrations 0001–0046 plus the staging seed and injected test duplicates: 8 contacts,
2 groups (1 safe exact duplicate, 1 shared contact identity), migration 0047 applied in 16 ms with every existing row
unchanged, foreign-key and integrity checks clean.

## 5. Deployment facts that shape the rollout

- Merging to `main` deploys **staging automatically** and applies migrations (after a D1 Time Travel bookmark).
- Production deploys only through the release workflow with Founder approval; migrations must stay additive.
- The repository is **public**: fixtures use `.example` domains and 555-01xx numbers; reports default to ids only.
