# Staging — setup (one time, about 10 minutes)

Staging is the real Crestmont platform running on Cloudflare with sample data. **Since 2026-10-28 (Founder
decision) the website is public:** it loads like a normal website, with no preview password. Owner, staff and
customer accounts keep their own sign-in, staff two-factor authentication is mandatory, and no real payments,
emails or phone calls happen there. Everything except the steps below is automated by
`.github/workflows/deploy-staging.yml`.

## What you do (once)

1. **Cloudflare account** — sign in or create one at https://dash.cloudflare.com (the free plan is enough).
2. **workers.dev subdomain** — in the dashboard open **Workers & Pages**. If asked, choose a subdomain
   (for example `crestmont`). The preview will live at `https://crestmont-platform-staging.<subdomain>.workers.dev`.
3. **API token** — **My Profile → API Tokens → Create Token → "Edit Cloudflare Workers" template**, then
   **+ Add more → Account → D1 → Edit**. Account resources: your account. Zone resources: none needed.
   Create the token and copy it (it is shown once).
4. **Account ID** — on the dashboard home page (right-hand column, "Account ID").
5. **GitHub secrets** — in `Schmidt-Development/Crestmont-Website-Development` → **Settings → Secrets and variables
   → Actions → New repository secret**:
   - `CLOUDFLARE_API_TOKEN` = the token from step 3
   - `CLOUDFLARE_ACCOUNT_ID` = the ID from step 4
   - **`ACCESS_ARTIFACT_PASSPHRASE`** = a random passphrase of **32+ characters**, generated by and kept only in
     your password manager. **Required**: artifacts of a public repository can be downloaded by anyone signed in to
     GitHub, so the access notes are sealed with this passphrase and are never issued without it. A credential
     rotation refuses to start without it (so you can never be locked out of the rotated Owner account).
   - **`EVIDENCE_INGEST_SECRET`** = `openssl rand -hex 32`, set once (docs/DEPLOYMENT.md §5). The same value is used
     by every workflow; without it staging uses a key derived from the Cloudflare token, and CI, releases and production release authorization cannot sign against staging.
6. **Run it** — **Actions → Deploy staging → Run workflow** (it also runs on every push to `main`).

## What you get

Each successful run downloads as a **staging-access-sealed** artifact (kept 7 days) containing
`staging-access.sealed`: AES-256-GCM with a scrypt-derived key, so it is unreadable and tamper-evident without
`ACCESS_ARTIFACT_PASSPHRASE`. Open it with Node.js 22.18 or newer and `scripts/seal.ts` (one self-contained file;
a repository checkout is not needed):

```sh
node --no-warnings scripts/seal.ts open staging-access.sealed
```

It asks for the passphrase without echoing it and prints the notes to the terminal (add a file name to write them
to a file instead, and delete that file when done). "wrong passphrase, or the file was modified" means exactly that.

After a **rotation** the Owner has no recovery codes: sign in, then Account → Recovery codes → enter a current 2FA
code, and save the new codes in your password manager. A rotation run also uploads **staging-forensics-sealed**
(the pre-rotation evidence, sealed the same way, kept 90 days). The notes hold, at the top: the website URL, the Owner email, the Owner
password and the Owner 2FA authenticator setup key, followed by every other demo account.

The artifact is issued **only after the run has verified the whole sequence on the live site**: public homepage
with no cookies → staff, portal and account areas refused anonymously → Owner email and password → staff area still
refused before 2FA → a valid 2FA code → all 32 Owner modules loading. If that check fails the
run fails and no artifact is issued, so an artifact never holds credentials that do not work.

How the credentials stay in sync: every run derives all demo credentials from the `CLOUDFLARE_API_TOKEN` secret
plus a random salt kept in the staging database, and re-applies them to the demo accounts. The newest artifact is therefore always correct, and credentials do not
change between runs unless they are rotated.

- **Rotate everything** (all demo passwords, the Owner's included, and 2FA keys; old sessions are signed out):
  re-run with **rotate_credentials** ticked. Re-add the Owner key to your authenticator afterwards.
- Rotating the Cloudflare API token also changes the derived credentials on the next run.
- Want fresh sample data? Re-run with **reseed_demo_accounts** ticked.
- The `STAGING_PREVIEW_PASSWORD` repository secret is no longer used; you may delete it.
- R2 (file uploads) is optional: if it is not enabled on the account the preview works and file pages say
  storage is not configured. Enable R2 in the dashboard to turn uploads on (R2 asks for a payment method even
  on its free tier — that is your decision).

## Staging browser evidence

After verification, every run also drives a real Chromium browser through staging as a fresh visitor (no cookies):
every public page
linked from the homepage, the customer portal (with tenant isolation) and every Owner module. Results are
recorded as **staging** evidence for TEST-002. The journey is read-only; it never submits business forms.
Rehearse locally with `tests/e2e/staging.e2e.ts` (see its header for the two variables).

## Safety properties (verified by tests)

- Public pages and assets load without authentication; every non-public route still requires its own sign-in
  (`tests/security-matrix.test.ts` covers every route), and staff areas require two-factor authentication.
- Not indexable: every Worker response carries `X-Robots-Tag: noindex, nofollow`, pages carry a noindex meta tag,
  and `robots.txt` is `Disallow: /`. Every page shows the "Staging environment — test data only" banner.
- Email is sent only to addresses on `EMAIL_RECIPIENT_ALLOWLIST`; everything else stays in the outbox. Demo
  accounts use the reserved `.test` domain.
- Sign-in, registration, password reset and lead forms are rate-limited per IP; sign-in also per email, with an
  8-attempt, 15-minute lockout.
- Turnstile still uses Cloudflare's documented always-pass **test** keys. Now that staging is public, create real
  staging Turnstile keys (Cloudflare → Turnstile) and set `TURNSTILE_SITE_KEY` (wrangler.toml) and the
  `TURNSTILE_SECRET` secret so public forms get a bot challenge.
- Staging has its own database; production is never touched by this workflow.
- **Emergency re-lock:** add `PREVIEW_GATE = "required"` to `[env.staging]` vars and set the `STAGING_ACCESS_PASSWORD`
  secret (`wrangler secret put STAGING_ACCESS_PASSWORD --env staging`). The gate fails closed (503) until the secret
  exists. Rolling back to a Worker version from before 2026-10-28 also re-locks staging, because those versions
  still carry `PREVIEW_GATE = "required"`.

## Changing the Owner password (Founder-controlled)

The staging Owner is the demo account `owner@crestmont-preview.test`. Its password and 2FA key are **derived and
re-applied on every staging deploy**, so a password changed inside the app (Account → Password) lasts only until the
next deploy. Use one of these instead. Neither ever shows a password in chat, logs or a plain artifact.

**A. Rotate (recommended).** Gives the Owner a new random 20-character password and a new 2FA key; revokes every
old demo password, 2FA key, session, recovery code and pending demo invitation, and proves over HTTP that the old
ones no longer work.
1. Confirm the `ACCESS_ARTIFACT_PASSPHRASE` secret is set (32+ characters, only in your password manager). Without
   it the run refuses to rotate, so you cannot be locked out.
2. **Actions → Deploy staging → Run workflow** on `main`, tick **rotate_credentials**, run.
3. When it is green, download **staging-access-sealed** and open it locally:
   `node --no-warnings scripts/seal.ts open staging-access.sealed` (asks for the passphrase without echoing it).
4. In your authenticator, delete the old "Crestmont staging" entry and add the new setup key; sign in at
   `/login`; then Account → Recovery codes and save the new codes.

**Choosing the exact password yourself** is not supported on staging today: the deploy always re-derives the
demo Owner's password, and `scripts/bootstrap-owner.ts` creates an invitation only when no Owner exists (staging
already has the demo Owner, so it would do nothing). A password changed in the app is real but temporary: it is
replaced by the derived one on the next deploy.

Lockout note: the demo Owner email is visible in this public repository, so anyone can deliberately trip its
sign-in lockout (8 wrong attempts → 15 minutes). It cannot be taken over that way (20-character random password
plus 2FA). The next deploy clears the counter.

Lost the authenticator and every recovery code? See `docs/RUNBOOK.md` §4a (`scripts/reset-owner-mfa.ts`).
